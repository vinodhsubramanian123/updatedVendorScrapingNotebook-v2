# Dashboard release gap plan

Reviewed 11 November 2026 against `127a2f08`. This plan covers the dashboard paths that take in customer data, run presales work, and produce downloadable results. It extends the [dashboard closure report](2026-11-11-dashboard-gap-closure-and-e2e-certification.md) with acceptance criteria for the remaining risks.

| Order | Priority | Work | Dependency |
| --- | --- | --- | --- |
| 1 | P0 | Enforce local-only policy before customer data reaches cloud adapters | Start immediately |
| 2 | P0 | Close diagnostic export and invalid-rank bypasses | Start immediately. Complete server-owned export binding after the run record is available |
| 3 | P1 | Make run identity, cancellation and recovery durable | Supplies the run contract for handoffs and export |
| 4 | P1 | Connect routed results to the evaluator without losing configuration scope | Use the run and intake contracts from step 3 |
| 5 | P1 | Add a production-mode browser release gate | Add focused regressions with each fix, then run the integrated gate |

## 1. Enforce local-only before OCR and grounding

**Finding.** Direct BOQ evaluation has an offline check. The preflight upload path calls Gemini OCR before checking execution policy, and the cross-vendor route also calls OCR on image/PDF input without an offline check. The routed query resolver accepts client `offlineMode: false` before consulting server offline flags. A configured cloud adapter can therefore receive a quote when the operator expects local-only handling. [Preflight](../../dashboard/routes/evaluation.cjs#L100) · [Routed policy](../../scripts/evaluators/route_query.js#L733) · [Competitor OCR](../../scripts/evaluators/route_query.js#L1391) · [OCR transmission](../../scripts/lib/ocr/ocr_service.js#L110)

**Implementation.** Resolve effective policy on the server before preprocessing or dispatch. An enforced server offline policy takes precedence over client fields. Persist effective policy on the intake and run, and carry it through clarification, retry, candidate evaluation and deferred grounding. Guard the OCR and NotebookLM dispatch points with that policy. For an image-only local request, return a structured action to supply pasted text or a supported tabular file. Give standalone notebook actions a local fallback or a clear unavailable state when the server enforces local-only mode.

**Acceptance.** With cloud adapter spies configured, submit a PDF and an image through preflight, routed competitor intake and direct evaluation. Repeat with a conflicting `offlineMode: false` under server offline mode. Every case records zero cloud adapter calls and returns an actionable outcome. Local text, CSV and XLSX still complete. An explicitly cloud-enabled fixture reaches the intended adapter once, and a deferred query for a local run is rejected before dispatch.

## 2. Export the exact authorized candidate

**Finding.** Both export endpoints accept a caller-controlled diagnostic flag. The workbook writer then skips delivery authorization and uses the ordinary workbook title and sheet layout. The route blocks some explicitly marked failures, so the diagnostic case concerns payloads that reach the writer. The writer also accepts a nonexistent rank after verifying the evaluation-level authorization and falls back to the original input BOM. A local in-memory probe confirmed both outcomes, including a workbook titled “Strategy Rank 999” containing the original input SKU. [Export routes](../../dashboard/routes/evaluation.cjs#L393) · [Authorization branch](../../scripts/lib/boq/generate_boq_xlsx.js#L20) · [Workbook title](../../scripts/lib/boq/generate_boq_xlsx.js#L113) · [Rank selection](../../scripts/lib/boq/generate_boq_xlsx.js#L227)

**Implementation.** First reject unsupported ranks and diagnostic overrides on the customer export endpoints. When an internal diagnostic workbook is needed, give it an explicit diagnostic label in the file and in the workbook, and keep it out of customer export history. Then resolve the product, rank and exact candidate from the server-held run, verify authorization and evidence against that candidate, and generate the workbook from those stored rows. Record run ID, product, rank, candidate digest, workbook digest and evidence state in export history. Derive download availability from server eligibility and return the reason when delivery is blocked. Keep vendor acceptance and delivery authorization visible as distinct evidence states.

**Acceptance.** Requests with a nonexistent rank, expired or mismatched authorization, changed quantity or product, a caller-supplied diagnostic override, or a blocked candidate produce no customer file or history entry. A valid export downloads successfully and its SKU rows, quantities, product, rank and workbook digest match the recorded candidate and artifact. Reopening the exact run yields its own export and evidence state. Internal diagnostics are visibly marked on opening and absent from customer export history.

## 3. Recover runs by ID and make cancellation precise

**Finding.** The dashboard stores per-run state in memory and persists only the latest BOQ and latest routed result in its snapshot file. Older task logs can survive in separate trace files, but the snapshot cannot restore their full results. The presales panel still accepts broadcasts by product alone. The cancel endpoint targets whichever run is active when the request arrives, so a stale tab can cancel a newer run. [Snapshot persistence](../../dashboard/services/runState.cjs#L5) · [Existing trace history](../../dashboard/routes/catalogs.cjs#L477) · [Routed result selection](../../dashboard/src/components/PresalesRequestPanel.jsx#L268) · [Cancel route](../../dashboard/routes/tasks.cjs#L137)

**Implementation.** Extend the existing history store with atomic run records and a run-by-ID read path. Persist identity, product, effective policy, input hash and reference, stage, terminal status, result or error, and evidence references. Acknowledge a routed run with its ID at submission, and have the browser subscribe to that run. Allow operators to reopen a historical run while showing current activity independently. Bind cancellation to the expected run ID and keep the task slot held until cleanup is confirmed. After restart, restore completed and waiting-for-input runs and mark unrecoverable in-flight work interrupted. Retain intake while clarification is pending within the retention window. Return a re-upload action when the original input expires or changes.

**Acceptance.** In two tabs, run two requests for the same product and verify each tab keeps its selected result. Drop the stream across completion and restart the backend during evaluation and during clarification. Recovery returns the correct terminal or interrupted status and preserves the older result. A stale cancel for run A leaves active run B untouched. Duplicate cancellation for B has one effect, and cancellation becomes terminal only once cleanup is confirmed. A changed or expired clarification input requires re-upload.

## 4. Preserve configuration scope through presales handoffs

**Finding.** The sizing route returns `candidateBOM` and `serverCount`, but the dashboard only looks at `items` and `evalResults.items` to render the BOM and show the evaluation action. Where the action is available, it serializes the candidate as plain SKU text and carries only the offline toggle. That handoff drops structured node count, cluster ownership and quantity scope. [Sizing response](../../scripts/evaluators/route_query.js#L1158) · [Outcome display](../../dashboard/src/components/PresalesRequestPanel.jsx#L173) · [Candidate handoff](../../dashboard/src/components/PresalesRequestPanel.jsx#L260)

**Implementation.** Give sizing and cross-vendor results a typed candidate reference tied to the originating run. Show the product, node or cluster count, quantity basis and missing requirements. Resolve that reference into the canonical evaluator's structured input with the originating product, quantities, ownership and policy. Preserve the parent run and candidate digest in the resulting evaluation. Route ambiguity back to an explicit clarification action before evaluation.

**Acceptance.** Submit the four-node sizing preset, review its candidate table and open the matrix evaluation. Verify four nodes and the original per-node and extended quantities in the evaluator result. Repeat with a mixed configuration fixture and assert that shared rows and node-owned rows keep their ownership. Changing the header's selected product during a request leaves the original candidate and its follow-up scoped to the original product. A draft with missing requirements displays the required clarification.

## 5. Require workflow evidence in the browser release gate

**Finding.** The current browser checks cover useful navigation and rendering. The basic check populates sample text without submitting it. The portfolio check can satisfy topology with a generic SVG and counts any table rows after a product switch. CI runs dashboard component tests, while these browser workflows lack a required job. The current green result leaves the highest-risk user journeys unverified. [Browser smoke](../../scripts/maintenance/test_dashboard_browser_e2e.js#L111) · [Topology check](../../tests/e2e/test_dashboard_full_portfolio_e2e.js#L166) · [Catalog sweep](../../tests/e2e/test_dashboard_full_portfolio_e2e.js#L225) · [CI workflow](../../.github/workflows/ci.yml#L27)

**Implementation.** Run a production build and isolated server against sanitized fixtures in CI. Add required journeys for BOQ upload and paste, clarification and resume, sizing to matrix, reconciliation, blocked and authorized export, two-tab isolation and cancellation. Assert terminal results and artifact contents against the run ID. Make portfolio checks assert product-specific evidence and topology nodes from the evaluated manifest. Check 390 px layout and keyboard navigation on the critical flows. Block external browser and server traffic in the offline job. Use separate, scoped live validation for HPE OCA/CLIC, NotebookLM grounding and cloud readback, with explicit coverage status for each.

**Acceptance.** CI fails for a missing required control, wrong product or run, unexpected network call, invalid export, missing artifact, or timeout. Release evidence records the tested commit, cases run, outcomes and skips. Keep the two P0 checks as release blockers for customer-quote and customer-export use. Close the dashboard workflow sign-off after the required P1 journeys pass. Track live service evidence per product and manifest.
